# Fact register

The single, current list of what is true about gymmy: product rules, behaviour, decisions, boundaries, plans and prices, one file per fact, in plain words. This index is loaded into every AI session.

- **Disagreement is a question, not a fix.** When a fact and the code, a doc, the app's copy or a Confluence page disagree, neither side wins: ask the owner, and change nothing until they answer. The weekly check opens one GYM issue per mismatch.
- **A decision is written down when it is made.** When the owner decides something, write or change the fact file in the same change and quote the sentence back to them.
- **Curated, never add-only.** Every update reviews the register as a whole: merge facts that overlap, rewrite the ones a change touches, and delete what no longer holds or no longer earns its place. A replaced fact is deleted, not kept — git history and the Decision log hold the reasoning. The register should get sharper over time, not longer.
- **A changed fact:** edit its file first, then every place listed under `appears` (repo docs, copy keys, tests, Confluence pages) in the same change. `planned` means decided but not built.
- `apps/web/src/lib/facts.test.ts` checks that every file is well-formed and every pointer under `appears` resolves. It cannot check that a sentence is true.

## Product

- [what-gymmy-is](what-gymmy-is.md) — gymmy plans a balanced training week and records what you lift. It shows which movements you covered, how each lift has changed and how strong you are compared with your past self.
- [coverage-thesis](coverage-thesis.md) — Most people who lift train only four or five of the seven patterns and never notice, usually missing rotation and loaded carries. Apps organised by muscle group cannot show that gap.
- [who-it-is-for](who-it-is-for.md) — The main user already trains or is coming back to it (not a beginner, not a competitor), two to four days a week, on a phone, with little time and no wish to design a programme. A second, deliberately narrow audience is the trainer who writes plans for other people.
- [not-served](not-served.md) — Not served on purpose: shared or supervised accounts, competition prep, typing in your own programme, anything social (no feed, following or leaderboard) and nutrition; bodyweight is recorded only because the strength numbers need it, and never commented on. A class can be logged only as the sets, reps and load of its movements; time, rounds, scores, running, rowing, the bike and burpees have nowhere to go.
- [describe-evaluate-prescribe](describe-evaluate-prescribe.md) — The app always describes, judges only where the person asked it to (a goal), and never prescribes: no suggested weight or reps, no 'add a rep' or 'ready for more weight' card, and no warning that a set looked too easy. Only a human trainer prescribes, through a plan shared in gymmy.
- [silence-is-success](silence-is-success.md) — Most accounts will never set a goal and never be told anything that judges them, and that is intended. Success means people training movements they used to skip, logging staying one tap, and a second goal after the first, not downloads.
- [no-rename-screen](no-rename-screen.md) — Nothing in the app lets a person rename an exercise or a pattern today. The data model allows it, but no screen does.
- [units-relabel](units-relabel.md) — Weights are stored in the profile's unit (kg or lb) as entered. Switching units relabels existing history instead of converting it.
- [onboarding](onboarding.md) — Setup runs once and asks five questions: the shape of the week, how many days, gym or home, an optional emphasis, and bodyweight (skippable), then previews the week. It never asks about slots, roles, patterns, sex or year of birth.
- [optional-profile](optional-profile.md) — Every profile field (picture, name, year of birth, sex, height) is optional and never invented; an empty name stays empty. Sex is used only for DOTS, year of birth only for the age allowance, and height by nothing yet; the picture is cropped square and stored in the profile row.
- [sign-out-wipes](sign-out-wipes.md) — Signing out tries one last sync, then wipes the device regardless, so the next person on that phone inherits nothing; signing out while offline loses sets that had not synced. So support must never tell someone whose training is missing to sign out, reinstall or clear site data: each wipes the device, which may hold the only copy.
- [data-export](data-export.md) — (planned) A self-service data export is agreed and queued but not built. Until then an access request is answered by hand with a JSON export.

## Training model

- [seven-movement-patterns](seven-movement-patterns.md) — Training is organised by movement, not muscle, into seven patterns: squat, hinge, lunge, push, pull, rotate and carry. Isolation work (curls, raises, calves) is tracked but never counts toward a complete week, under any split.
- [no-unfair-verdicts](no-unfair-verdicts.md) — The app says only what it can stand behind. If one end of a comparison has effort recorded and the other does not (an unrated set reads about 5% lower), it gives no verdict rather than a softened one.
- [split-history](split-history.md) — Changing split starts a period from this Monday (a second change that week replaces it) and never edits an older one; each period freezes what counted as a complete week. Every week is scored against the split in force that week, marked 'Scored as' and that split's name when it differs.
- [split-presets](split-presets.md) — Four split choices: seven patterns (2–4 days, complete means all seven), Push/Pull/Legs (3–6 days) and Upper/Lower (2–6 days), both complete with push, pull, squat, hinge and lunge, or your own. Only the seven-pattern split asks for rotation and carry, and a day count a split cannot cover is not offered.
- [build-your-own](build-your-own.md) — Settings → Build your own starts from the current week: slots can be tied to movements or roles, moved with ↑/↓ (no drag-and-drop yet), added or removed, up to six days, with a preview of what counts as complete. A custom split keeps the goal of the split it grew from, minus any pattern no slot can hold.
- [generated-week](generated-week.md) — A generated day has five slots, each exercise 3 sets: 6–12 reps for main lifts, 10–15 for isolation and 30–40 m for the finisher. Push/Pull/Legs and Upper/Lower add a rotation-or-carry finisher every day as a bonus, and a repair pass fills any gap so a generated week always covers its split's patterns.
- [generator-variety](generator-variety.md) — 'Home' limits the week to the 53 exercises marked as working at home (mostly dumbbells, kettlebells and bodyweight) and 'Gym' uses the whole library; an emphasis (shoulders, arms, glutes, back or chest) gets a little extra. A fixed per-account offset gives two people with the same answers the same shape but different exercises.
- [week-changes-on-request](week-changes-on-request.md) — A week is generated only on joining, 'Rebuild my week', changing split or applying a plan, never on its own, and rebuilding never touches a logged set. Rotating in exercises you have not done lately is deliberately not built, because a rebuild could drop a lift someone has a goal on.
- [off-plan-movements](off-plan-movements.md) — 20 conditioning movements (Olympic lifts, thrusters, wall balls, box jumps, ring and bar gymnastics, Turkish get-ups, sandbag carries) can be logged and a trainer may name one, but the generator never programs them and they are never offered as swaps. Everything logged counts the same way.
- [log-something-else](log-something-else.md) — 'Log something else' below Train's planned cards logs any catalogue exercise, stored as ordinary set logs under the reserved session label X. Those sets count for coverage, both strength numbers, goals, charts, 'last time' and the session count, but never tick a planned day; picking a lift the open day plans opens that day's own card.
- [e1rm-rule](e1rm-rule.md) — The estimated one-rep max (Epley, adjusted for reps in reserve) is worked out only when reps plus reps in reserve are ten or fewer; past that it is blank, not zero. The cost was accepted: at the default answer only sets of 8 reps or fewer give an estimate (demo account: 77% of sets down to 39%).
- [lift-charts](lift-charts.md) — A loaded lift charts its best estimated one-rep max per session; a lift trained only for high reps, and every isolation lift, charts its heaviest set instead, and the label says which. 'Last trained' is the day the lift was logged, not the last day it added a point to a chart.
- [two-strength-numbers](two-strength-numbers.md) — Progress shows two strength numbers: gymmy's strength index ('am I getting stronger?') and DOTS ('how do I compare?'). Both come from the last eight weeks of estimates (the scored week and the seven before it) and read higher than a meet total, which the screen says; the index shows in the tens with one decimal, DOTS as a whole number in the hundreds.
- [strength-index](strength-index.md) — The strength index adds the best estimated one-rep max in squat, hinge, lunge, push and pull over the last eight weeks and divides by bodyweight to the power 2/3; a pattern never trained counts as zero, and it is only ever compared with the same person's past. Only barbell, dumbbell and kettlebell lifts count, plus pull-ups, chin-ups and dips at that week's bodyweight plus what was added; machines, partial loads and other bodyweight moves never do.
- [age-allowance](age-allowance.md) — The strength index gets an age allowance from 40 (about ×1.13 at 50, ×1.34 at 60, ×1.65 at 70, straight lines between), using the person's age that week from their birth year. There is none below 40, and DOTS never has one.
- [dots](dots.md) — DOTS uses only barbell back squat, bench press and conventional deadlift, the published per-sex formula and no age factor. It is blank, never smaller, until all three have an estimate in the last eight weeks, there is a bodyweight and sex is male or female ('prefer not to say', the default, leaves it blank), and the screen says which is missing.
- [carries-rotation-unmeasured](carries-rotation-unmeasured.md) — Carries and rotation never count toward either strength number, have no chart and get no verdict of any kind, not even 'Not trained'. Their reps are metres or seconds, and their sets still count for coverage.
- [load-classes](load-classes.md) — Every exercise declares a load class: barbell, dumbbell pair, single dumbbell, machine (Smith machine included), bodyweight or partial load (landmine, sled). Machine, added-bodyweight and partial loads are not real masses: they are charted against themselves and reach neither strength number. The one exception is pull-ups, chin-ups and dips, where near enough the whole body moves: the strength index counts them at bodyweight plus what was added.
- [dumbbell-pair](dumbbell-pair.md) — For a dumbbell pair you enter one dumbbell and the pair is stored (enter 20, 40 kg is recorded); only Train's weight box converts, and every other screen shows the stored figure. This started on 2026-09-17, older logs are never rewritten, and a chart notes the date only where the lift really jumps (1.5× or more).
- [goals-grant-permission](goals-grant-permission.md) — The app judges a lift's progress only where the person set a goal on it: one lift, a target estimated one-rep max and an end date, which expires and never renews. Without a goal the 'Down' and 'Not moving' verdicts are withheld; 'Not trained' needs no goal.
- [goal-guardrails](goal-guardrails.md) — A goal must be at least 5% above where the lift is now (retests vary about 4%), rest on at least three sessions in the last eight weeks, and run 8 to 52 weeks, with at most three running at once. A goal needing more than 1.5 times the lift's own pace over the last six months (or a published rate, without that history) gets a warning, never a refusal.
- [goal-no-pace](goal-no-pace.md) — A goal shows no expected pace and no 'behind by' line, only whether the lift has moved beyond retest noise.
- [goal-endings](goal-endings.md) — A goal ends as reached, part of the way (showing what was added) or flat, never as 'failed'. 'Part of the way' needs the lift to have moved beyond day-to-day noise (about 4%); less than that ends as flat, so 100 → 110 ending at 102 is flat. An ended goal stays on Progress for three weeks with 'Set another', and 'Stop pushing this' ends one at once, keeping it as retired rather than deleted.
- [verdict-thresholds](verdict-thresholds.md) — Down: the best of the last three sessions is 5% or more below the lift's best, and that best is not recent. Not moving: no new best in 8 weeks across at least 6 sessions. Not trained: still in the week but untrained for 3 weeks, checked before Not moving; a month at one weight is not a stall.

## Screens and copy

- [plain-words](plain-words.md) — Confluence pages and app copy are compact and written in plain, everyday words.
- [five-languages](five-languages.md) — The app is in English, Magyar, Deutsch, Français and Español, exercise names included (English kept where lifters say it, like Face Pull). The language follows the account, switches without a reload, and a missing translation fails the build.
- [save-status-visible](save-status-visible.md) — Every save reports its own failure. The header's sync dot is green when saved, amber offline and red when a change is saved on this device but not synced yet. A change not saved on this device at all shows a magenta warning triangle and a line of warning under the header instead, so the two never look alike, and both stay until the person dismisses the warning, whatever the sync does next.
- [goal-entry-point](goal-entry-point.md) — A goal can be set only from one lift's detail sheet ('Push this lift'), and nothing in the app advertises goals. The form offers 8, 12, 16, 24 or 52 weeks and prefills a target that passes every check; a trainer can never set a goal on somebody else's lift.
- [worth-knowing](worth-knowing.md) — Progress opens with 'Worth knowing': at most three lifts, taking one of each verdict in turn (Down, Not moving, Not trained). The card is absent when there is nothing to say and no goal is set; with a live goal and nothing to say it reads 'Nothing to flag.'
- [tabs](tabs.md) — Five tabs in this order, swipeable: Home, Train, Week, Progress, Settings. Trainers reach a Coaching screen from Settings; it is not a sixth tab.
- [home-screen](home-screen.md) — Home shows today's session, the week's coverage so far and a Monday-first calendar. Tapping a trained day shows its sets, the strength index as it stood that week and bodyweight.
- [train-screen](train-screen.md) — Train has a tab per plan day (Day A up to Day F) and opens on the first day not yet trained this week. One exercise card is open at a time and finishing it opens the next; a day is ticked once every planned set is done that week, on any date.
- [train-last-time](train-last-time.md) — A Train card prefills last time: the heaviest weight in the latest session on that lift and the fewest reps at it, labelled as history ('Last time 60 kg × 8 · date'). With no history it starts at neutral numbers (empty bar, 10 kg dumbbells, 20 kg machine, no added weight), a starting point rather than advice.
- [effort-in-words](effort-in-words.md) — Each set records how it felt, chosen in words on the card: Nothing left, 1 more, 2 more or Easy (stored as 0, 1, 2 or 4 reps in reserve; default 2 more). It never shows a number or 'RIR', and the answer feeds only the one-rep-max estimate.
- [no-phone-keyboard](no-phone-keyboard.md) — Train never opens the phone's keyboard: weight and reps are set with Buttons (default) or a Ruler, and tapping a number opens gymmy's own keypad. 'Load the bar' (on by default) shows barbell weight as plates. Every weight on a scale is written with the same decimals (60.0, 62.5; whole kilos stay whole) on every control, so the number keeps its width as it changes.
- [prefs-follow-account](prefs-follow-account.md) — Settings preferences (language, theme, kg or lb, entry mode, Load the bar) belong to the account and follow the person to another phone; theme defaults to following the device. Only the bar weight picked on a Train card stays on that phone, remembered per exercise.
- [week-tab](week-tab.md) — The Week tab opens on this week and pages back to the week the account began, or to the first logged set if that is earlier; a new account can also page ahead through its first eight weeks. It shows the week's coverage in words, a tile per movement the split in force asks for and the session count, then the plan day by day. A swap (the same searchable picker as 'Log something else') keeps the movement in most slots, but a full-body day's big-lift slots and every finisher offer any lower, upper or core movement, so a swap there can change coverage.
- [progress-layout](progress-layout.md) — Progress has up to five sections: Worth knowing, What you are pushing (live goals), Strength, What you have trained (12 weeks by 7 movements) and Every lift; the first two are absent on most accounts. Change arrows compare with eight weeks ago and never rely on colour alone.
- [motion-ux-planned](motion-ux-planned.md) — (planned) A swiped page will follow the finger, tab changes will not pile up in browser history, Settings will use native switches, and explanations will sit behind ⓘ icons instead of paragraphs.

## Data

- [store-what-happened](store-what-happened.md) — The database stores what happened, never what it means. A set holds weight, reps and reps in reserve; every derived number (estimates, charts, strength numbers, verdicts) is worked out when read.
- [twenty-tables](twenty-tables.md) — There are 20 tables: 9 synced ones for a person's own training (patterns, legacy exercises, slots, split periods, program entries, set logs, body logs, goals, profile), 6 for trainer plans and 5 for sign-in. Every synced row carries a last-changed time, a soft-delete marker and a change number that only the server sets.
- [new-field-rollout](new-field-rollout.md) — A new column or synced table does not reach devices already synced or one build behind. New fields need a default where rows are read (prefs() for settings), and code that reads a field ships one release before code that writes it.
- [account-deletion](account-deletion.md) — 'Delete your account' in Settings says how many sets and weeks will go, then really deletes: the device is wiped without a final sync, sign-in codes and attempts for the address go first, and one delete cascades from the user. It cannot be undone; soft deletes exist only so a delete reaches offline devices.
- [seeding](seeding.md) — A new account gets the seven patterns plus isolation, a seven-pattern 3-day week, an opening split period and a profile, but no exercise rows. Seeding runs only on an empty account, so new defaults reach new accounts only; existing users need a backfill.
- [exercise-catalogue](exercise-catalogue.md) — The exercise library is one catalogue in code, shared by every account; people cannot add their own, and a new entry reaches everybody on the next deploy with no migration. It holds 105 exercises (85 the generator can program, 20 off-plan), each with a short English-only description (names are translated), and 57 have two public-domain photos stored with the app.
- [exercise-ids-permanent](exercise-ids-permanent.md) — Catalogue ids are written out (ex-barbell-back-squat), never computed, and every id ever published keeps working. No stored id is ever rewritten: older accounts' own exercise rows are read as aliases of catalogue entries, matched by name, and an exercise is retired rather than deleted, keeping its name and chart in history.
- [exercise-names-frozen](exercise-names-frozen.md) — Catalogue exercise names are frozen in English for now, because descriptions, photos, load classes and translations are keyed by them. Renaming one fails the tests.
- [bodyweight-record](bodyweight-record.md) — Bodyweight is a dated record, one reading per day (a second one that day replaces the first). Each week's strength numbers use the latest weight up to the end of that week, and neither number exists without one.

## Architecture

- [local-first](local-first.md) — The phone holds all of a person's training and every screen reads from it, never waiting on the network; the server is a copy that catches up. Logging a set never fails for lack of signal, and sets logged offline sync later.
- [one-sync-endpoint](one-sync-endpoint.md) — All training data moves through one endpoint, POST /api/sync, which sends local changes and fetches newer ones in one round trip. There is no REST route per table, and changes are ordered by one Postgres sequence, not by clocks.
- [last-write-wins](last-write-wins.md) — When two devices change the same record, the most recent write wins, judged per record by updatedAt; there is no CRDT. Deletes are soft so they can reach a device that is offline.
- [domain-rules-pure](domain-rules-pure.md) — All training rules live in packages/domain as pure functions with no runtime dependencies, so the same rules run on the phone, on the server and in scripts. The build enforces this.
- [db-sessions](db-sessions.md) — Sign-in sessions are database rows, not JWTs, and last 90 days. Deleting the row signs that session out at once.
- [two-outside-systems](two-outside-systems.md) — gymmy talks to exactly two outside systems, both only for sign-in: Google and Resend (the code email). There is no analytics, crash reporter, push service, payment provider, object storage or feature flags, and training data is never sent to any third party.
- [never-a-dead-end](never-a-dead-end.md) — The app never leaves a person stuck: a crash offers a reset, a stuck loading screen gives up after 12 seconds, a boot watchdog shows a message even if the app fails to load, and the server repairs an account that was never set up. Known exceptions, being specced from their root causes (GYM-57): a change the server rejects blocks syncing until sign-out, and a half-finished setup is not repaired.
- [sign-in](sign-in.md) — Sign-in has no password: Continue with Google, or a six-digit email code (valid 10 minutes, once) shown only when RESEND_API_KEY is set. Code requests are limited per address and per client, and every outcome looks the same, so nobody can find out who has an account.

## Trainers and programmes

- [trainer-role-manual](trainer-role-manual.md) — Today the trainer role is set only by a manual database change (user.role = 'trainer'), with no self-service. Every trainer write re-reads the role, so removing it takes effect at once.
- [coaching-screen](coaching-screen.md) — On the Coaching screen a trainer builds a plan from a shape and a day count, and for each slot names a catalogue exercise or leaves it to the app. A draft is private; once published, each edit makes a new version.
- [plans-server-only](plans-server-only.md) — Trainer plans, groups and shares live only on the server, outside the sync set, and are read over a small API that checks access on every request. They are the only training feature that needs a connection.
- [plan-sharing-today](plan-sharing-today.md) — Today a trainer shares a published plan with one person by email or with a group; shares are revoked, never deleted. Sharing with an address that has no account succeeds silently, and a plan you cannot see answers exactly like one that does not exist.
- [applying-a-plan](applying-a-plan.md) — Applying a shared plan copies it into the athlete's own account as slots, a new split period and a generated week; after that nothing knows a trainer was involved and it works offline. Exercises travel by name, so a missing one costs that exercise, not the session, and an athlete loses nothing if the trainer leaves or revokes the share.
- [plan-updates-offered](plan-updates-offered.md) — When a trainer publishes a newer version of a shared plan, the athlete is offered it, labelled 'Updated', and it is never applied for them. A trainer's edit never rewrites a week somebody is in.
- [one-way-sharing](one-way-sharing.md) — Sharing is one-way today: a trainer cannot see how anybody trains, and there is no compliance view, progress report or supervisory screen. Changing that is a privacy decision, not a feature.
- [plan-audit-log](plan-audit-log.md) — Everything done to a plan or group, deleting it included, is recorded in an append-only log (plan_events). It keeps the event and a copy of the name after the plan, group or person is deleted.
- [programmes-v1](programmes-v1.md) — (planned) Programmes, where a trainer runs somebody's training through gymmy, start with one trainer and one client and two roles, Person and Trainer; a trainer belongs to a practice (a practice of one is fine), and Company and Agency roles come later. Not in the first version: employer accounts and reports (a pilot is reported by hand), the monthly client report, goals set by a trainer, chat, paid programmes and automated qualification checks. Still open: where swap alternatives live so they work offline, and a lawyer's read of the consent wording.
- [trainer-self-serve](trainer-self-serve.md) — (planned) The first sign-in will ask 'Training' or 'Trainer', and anyone can later choose 'I also coach people' in Settings by creating or joining a practice and writing a profile. A trainer can stop only once nobody is enrolled in their programmes; each is handed to another trainer (trainees consent again) or ended, and trainees keep the last plan.
- [programme-shape](programme-shape.md) — (planned) A programme is a plan, its trainers and optional dates: none means ongoing coaching, a start date means a cohort, start and end mean a fixed block. People join by a link or QR code, and a person is in one programme at a time, keeping their history when they switch.
- [programme-consent](programme-consent.md) — (planned) Joining is not consenting: a separate step names each trainer, and a person can decline and still train the programme. Consent is an append-only history of dated grants and withdrawals, never a yes/no flag; leaving and withdrawing are separate one-tap actions, and adding a trainer needs everyone's consent again.
- [trainer-visibility](trainer-visibility.md) — (planned) With consent, a programme's trainers will see attendance, every set (with effort, swaps and training outside the plan) and progress (charts, the strength index, goals; DOTS only if sex was given). They never see bodyweight, year of birth or sex, every look is logged where the person can see it, and without consent they see only that the person is enrolled.
- [programme-week-follows](programme-week-follows.md) — (planned) Inside a programme the week follows the trainer's latest published plan automatically, labelled 'Updated by' and the trainer's name; history never changes and leaving keeps the last version. A trainee can swap only to the trainer's listed alternatives, for that day only; rebuilding and changing split are off, and Log something else still works.
- [trainer-clients-tab](trainer-clients-tab.md) — (planned) Trainers will work in an online-only Clients tab on phone or desktop; a trainee's data is fetched fresh and never stored on the trainer's device. A trainee can write a note on a session and the trainer can reply (one thread per session, not a chat), and web push will announce plan updates, new notes and replies.
- [programmes-replace-sharing](programmes-replace-sharing.md) — (planned) Sharing plans by email address or group will be retired over two deploys, leaving programmes as the only way to get a plan to a person. Plans stay as the trainer's library.

## Pricing

- [trainer-subscription-first](trainer-subscription-first.md) — (planned) The first thing gymmy will charge for is a trainer subscription; nothing is billed today. People who train never pay for their own logging, history, export, consent or deletion.
- [trainer-tiers](trainer-tiers.md) — (planned) Two tiers per trainer seat: Starter at €19 a month or €190 a year for up to 10 active trainees, and Pro at €39 a month or €390 a year with no limit. A practice picks one tier for all its trainers, pays per seat and gets one invoice.
- [trainer-trial](trainer-trial.md) — (planned) Each new trainer gets one 14-day free trial, once per person. Starting it needs a payment method, and it becomes a paid subscription unless cancelled.
- [stripe-billing](stripe-billing.md) — (planned) Trainer billing will run on Stripe Billing, not Paddle, because Paddle bans products that let others sell. Checkout follows German consumer rules: a 'zahlungspflichtig bestellen' button, an always-present cancel button, a two-step withdrawal button and 14 days to withdraw.
- [unpaid-pause](unpaid-pause.md) — (planned) When a trial or subscription ends unpaid, the trainer's programmes pause: trainees keep training on the last plan, and the trainer loses the Clients tab and cannot publish. After 30 days unpaid the programmes end and trainees keep the plan; paying before then restores everything.
- [paid-programmes-later](paid-programmes-later.md) — (planned) Paid programmes that trainees buy, with gymmy taking a cut, come later, after tax and legal opinions (VAT seller rule, DAC7 reporting, distance-learning law). Any cut stays low on a trainer's own clients; 20–30% applies only to buyers gymmy brings in.
- [never-hold-money](never-hold-money.md) — gymmy must never hold trainees' money in its own account, which would need a BaFin licence. Any programme sales go through a licensed provider, such as Stripe Connect with direct charges.

## Business

- [web-app-only](web-app-only.md) — gymmy is an installable web app with no App Store or Play Store version, so app-store fees (EU, from 1 October 2026) never apply. An installed copy updates itself after a deploy, reloading the next time it is out of view, with no store update.
- [consumer-subscription-rejected](consumer-subscription-rejected.md) — A consumer subscription is rejected as the main route: Hevy's free tier caps the price near €3, and fitness apps lose 10–13% of subscribers a month. A niche consumer product priced like coaching (€8–12 a month) stays open.
- [bgf-primary-bet](bgf-primary-bet.md) — BGF (German workplace health promotion, paid by the employer) is gymmy's primary business bet. The coach layer comes first because BGF needs the same foundation (organisations and an instructor role), so one build serves two revenue paths.
- [roadmap-order](roadmap-order.md) — (planned) Planned order: now, rename, deploy, the Coverage audit and insights over MCP; next, organisation tenancy, the instructor role and the yearly rewind; later, the instructor partnership and BGF pilots, with the certified-study design in parallel.
- [coverage-audit](coverage-audit.md) — (planned) The Coverage audit will be a free page, with no signup, that reads a Hevy or Strong export entirely in the browser and shows movement-pattern coverage, with no upsell before the result.

- [rejected-routes](rejected-routes.md) — Rejected: gym and studio white-label, a DiGA prescription app (needs medical-device certification), selling the sync engine, and a social feed. Two feed ideas are kept: a yearly rewind ('2026 in movement') and a shared week view for a few training partners.

## Workplace health (BGF)

- [bgf-tax-basis](bgf-tax-basis.md) — BGF rests on §3 Nr. 34 EStG: employers can spend €600 per employee a year on health, free of tax and social contributions, for prevention only (gym memberships excluded). Commercially sold prevention courses carry 19% VAT, and workplace accident insurance does not cover participants.
- [bgf-two-doors](bgf-two-doors.md) — Door 1 is employer-funded under §20b, needs no app certification and takes about six months; Door 2 is ZPP certification, takes 12–24 months, needs a pre-registered study and cannot be a subscription. Door 1 comes first and supplies Door 2's study participants.
- [bgf-distribution](bgf-distribution.md) — (planned) BGF is planned to be sold through 123datei's benefits catalogue: gymmy is the seller, and the tax firm runs the benefit in payroll with no commission and no client data. One programme across a tax firm's clients pools small employers (under about 50 staff) into groups big enough to report on.
- [bgf-price](bgf-price.md) — (planned) Working BGF price: €5 per employee per month (€60 a year, well inside the €600 allowance), so a 200-person client pays €12,000 a year.
- [bgf-employer-aggregates](bgf-employer-aggregates.md) — (planned) In BGF an employer sees aggregates only, never one person's results, and no setting can change that; it sees who is enrolled (a payroll fact), and a withdrawal shows only as 'no longer enrolled'. Whoever sells to companies sees only commercial data, employer and trainer screens never share a query path, and the account always belongs to the person, not the employer.
- [bgf-min-group](bgf-min-group.md) — (planned) No BGF figure is published about a group smaller than 5 people, and figures that would let someone subtract their way down to a smaller group are suppressed too. Reports are stored as issued, recording the floor used, and a later account deletion does not change them.
- [bgf-status](bgf-status.md) — BGF readiness today: German throughout, account deletion and an audit-grade data model are done; organisations, the instructor role, aggregate reports, consent and participation tracking are missing. First steps before building: settle ownership, find one certified instructor, and run one 8-week block with a friendly employer, reported by hand.
- [no-medical-claims](no-medical-claims.md) — gymmy stays a training and documentation tool: no diagnosis or treatment claims (claiming to treat back pain could make it a medical device) and no advertising. Do not pitch back pain as the top cause of sick leave; in early 2026 it fell to third.
- [bgf-open-questions](bgf-open-questions.md) — Open BGF questions: whether a certified strength programme counts as a medical device (the most important), VAT on the employer route, and whether NIS2 applies.

## Operations and docs

- [hosting](hosting.md) — Production runs on Vercel from main, with a preview per pull request, on Neon Postgres; each deploy runs migrations first over the unpooled URL, and a failed migration fails the deploy. Previews share the production database unless pointed elsewhere, and there is deliberately no queue, cache, cron, worker or separate API service.
- [drop-table-two-deploys](drop-table-two-deploys.md) — Dropping a table takes two deploys: stop using it, then drop it after counting its rows in production.
- [demo-account](demo-account.md) — The demo account (demo-gymmy@yopmail.com) is an ordinary account on the same code path, with 22 weeks of generated sets that come out the same every time: a stall, a slide, gaps and an abandoned lift, plus bodyweight, male, 181 cm and two goals. Reset it with 'npm run seed:demo -w @athletic/web -- --force'.
- [gdpr-requests](gdpr-requests.md) — GDPR requests are answered within one month, and erasure goes through Settings → Delete your account. After a backup restore, erasures made since the restore point must be done again.
- [fact-register](fact-register.md) — What is true about gymmy is written once, in docs/facts/: one file per fact saying where else it is stated, kept by the rules at the top of the index that every AI session loads. Other docs live in the repo (for whoever edits the code) and on Confluence (for everyone else), where the Decision log is only appended to and old entries are marked superseded. When any of these, the code or the register disagree, nobody picks a winner: the owner is asked.
- [graph-kb-rejected](graph-kb-rejected.md) — A graph knowledge base for the docs was considered and rejected: it answers questions nobody here asks and cannot be edited in a pull request. A graph would earn its place only if a script generated it from the source.
- [checked-docs](checked-docs.md) — docs/openapi.yaml is the API contract and a test holds it to the server's row schemas, so Confluence never re-describes endpoints or fields. The database diagrams are generated from the schema, a test fails when they are stale, and nobody draws them by hand.
